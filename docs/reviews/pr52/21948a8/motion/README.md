## 이전 공백을 확인하고 시도한 방법

[모모 리뷰](https://github.com/mrkimkim/infinite-gacha-defense/pull/52#issuecomment-6105088559)의 원본673233b frame log를 직접 대조했습니다. 390의 5.622357→5.889187초는 **266.830ms**, 1165의 5.609509→5.872562초는 **263.053ms**이며 모두 첫 접촉 시각을 가로지릅니다. [검증 기록](673233b-gap-verification.json)에 원본 로그 해시·양끝 프레임·시각을 보존했습니다. 동영상 변환에서 생긴 공백이 아닙니다.

최신21948a8에서 먼저 CDP screencast를 메모리 버퍼링·즉시 ACK로 바꾸고 공격 중 파일 쓰기/스냅샷 조회/인코딩을 제거했습니다. PNG와 JPEG95 각각 실행했지만 첫 접촉 공백은 약266.5ms로 남았습니다. [PNG 진단](cdp-comparison/png-diagnosis.json), [JPEG 진단](cdp-comparison/jpeg95-diagnosis.json) 및 해당 전체 프레임 시각 로그를 함께 제공합니다. 같은 구간의 게임 audit에는 접촉·회복 상태와 RAF가 계속 존재합니다. 실패한 원본 이미지 전체는 로컬에 보존하며 이 묶음에 포함하지 않았습니다.

그 다음 표준 `HTMLCanvasElement.captureStream(60)` + `MediaRecorder`로 **실제 게임 canvas**를 직접 녹화했습니다. clone한 스트림의 `MediaStreamTrackProcessor`가 각 실제 프레임의 timestamp를 기록합니다. 이는 캡처 경로만 바꾼 것으로, 게임 시계·RAF·피해·속도·포즈·타깃을 변경하거나 상태를 주입하지 않았습니다. 변속·보간·프레임 복제도 없습니다. 이 경로에서 첫 접촉 픽셀이 확인되므로 게임 canvas 자체의 첫 접촉 미그리기로 단정할 근거는 사라졌습니다. CDP/페이지 합성 경로가 빠뜨린 정확한 내부 원인까지 규명한 것은 아닙니다.

## 먼저 볼 공격 구간과 실제 간격

seed5 실제 UI로 누리를 (0,3), 포포를 (1,3)에 영입·배치한 뒤 1웨이브를 시작했습니다. 두 viewport를 순차 실행했으며, 가상 시계·정지·슬로모션을 사용하지 않았습니다. 원래 세 기물 실행과 달리 즉시 공격 placeholder는 영입하지 않아 효과 겹침을 줄였습니다. 두 캐릭터 사이의 타격·타깃 취소는 여전히 실제 게임 규칙대로 발생합니다.

포포 첫 접촉은 약4.68초, 다음 접촉은 약5.28초입니다. 편지 비행·적 테두리 접촉 cue·피격 색·회복이 실제 프레임에 존재합니다. 누리의 물방울과 뒤따르는 청록 반응·범위 원·회복/idle도 두 완료 공격에서 확인했습니다. 작은32px 몸체와 효과의 최종 가독성·자연스러움 판정은 독립 검토가 필요합니다.

구간 간격은 **실제 track timestamp 인접 프레임 차이**로 계산했습니다. [검증 표](video-verification.json), 각 viewport의 [390 캡처 로그](390/capture.json) / [1165 캡처 로그](1165/capture.json), [390 상태 전이·접촉](390/analysis.json) / [1165 상태 전이·접촉](1165/analysis.json)에 세부 수치가 있습니다. audit의 wall time을 영상에 붙인 안내 시각은 프레임 수신시각과 track timestamp 차이의 중앙값으로 추정한 값이며 전달 지연이 포함됩니다. 정확한 동시성 증명으로 쓰지 말고 픽셀·원본 PTS와 함께 보세요. 약4.68초 같은 반올림 안내와 frame timestamp 간격 측정은 구분합니다.

**중앙/가장자리 조건:** 현재 적은 보드 안이 아닌 바깥 사각 경로를 이동합니다. 보드 내부 중앙 피격을 상태 조작 없이 만들었다고 주장하지 않습니다. 포포 첫 접촉은 오른쪽 변 (canvas330,288), 두 번째는 오른쪽 아래 모서리 근처 (322.8,360), 누리 두 완료 접촉은 아래 변 중간 쪽 (233.4,360)입니다. 범위 원이 canvas 아래에서 잘리는 기존 표현과 옅은 파문은 그대로입니다. 타깃 경로·범위·피해는 바꾸지 않았습니다.

## 남은 실제 표시 상태와 수정 제안

포포는 조밀한 연속 공격에서 회복 후 바로 다음 준비로 넘어가므로 매 공격마다 자연스러운 idle 구간이 있는 것은 아닙니다. 중간의 일부 `idle`은 `unsupported:true`인 방향 fallback 상태이므로 완전한 회복→idle 성공으로 세지 않았습니다.

더 구체적으로, 두 실행 모두 마지막 공격26의 타격으로 **tick335·preparation**에 들어간 뒤 포포(unit2)가 `recovery`, 누리(unit1)는 `idle`입니다. 20초 실시간 대기 후 가져온 [390 snapshot](390/snapshot.json)·[1165 snapshot](1165/snapshot.json)에서도 같습니다. 녹화 프레임은 약16.78초의 마지막 그리기에서 끝났으며 남은 정지 화면 시간을 프레임 복제로 채우지 않았습니다.

현재 `src/web/schema4-play/presentation.ts`는 최근 타격 여부(`o.tick - shownTick <= 8`)로 recovery를 정하고, preparation에서 scheduler가 tick을 진행하지 않으므로 마지막 회복 조건이 만료되지 않는 설명과 일치합니다. **포포의 종료 후 idle 복귀 미확인은 캡처 간격만의 문제가 아닙니다.** 후속 후보로 core tick/피해/리플레이를 건드리지 않는 presentation 종료 포즈 수명 정책을 검토할 수 있습니다. 마지막 피격 증거·접촉 history는 유지하면서 회복 뒤 idle로 돌아오는 규칙과 별도 실시간 회귀 검사가 필요합니다. 이번 작업에서는 구현하지 않았습니다.

## 포맷·무결성·재생 확인

- 두 원본 WebM은 VP9, 요청 bitrate5Mbps의 **손실 압축**이고 약0.80MB씩입니다. MP4는 해당 실제 프레임을 H.264 CRF18/yuv420p로 한 번 더 손실 압축한 편의본이며 약0.20MB씩입니다. 원본 WebM을 함께 제공해 재압축 영향과 구분합니다.
- 두 실행 모두 track log·WebM·MP4에 **1,007프레임**이 대응합니다. 영상 PTS와 track timestamp 차이는2ms 미만이며 WebM의 밀리초 단위 시각 양자화가 포함됩니다. 60fps를 요청했지만 고정 간격을 강제하지 않았습니다. 모든 출력 프레임을 전부 디코딩했고 오류가 없었습니다.
- 약20초 동안 게임을 그대로 실행했으나 마지막 변화 후 canvas가 새 프레임을 내지 않아 파일의 실제 길이는 약16.8초입니다. MP4의 마지막 sample duration에 따른 약16ms 차이가 있으며 속도를 변경한 것이 아닙니다. 끝부분을 복제해20초로 늘리지 않았습니다.
- [Chromium 전체 1배속 재생 결과](playback-verification.json): 두 MP4 모두 ended, 오류 없음. 동시 재생에서 browser droppedVideoFrames는0/4였으며 화면 콜백 수는 파일 프레임 수와 다릅니다. 모든 프레임을 인간이 연속 감상했다는 주장은 아닙니다.
- 두 replay를 현재 core의 `replay(header,entries,finalHash)`로 다시 검증해 통과했습니다. 최종 해시는 양쪽 모두 `1afa2867b3a81c96457898f5002212c532e5140050d8147bf13f9a56de548580`입니다. 전체 기존 테스트는 반복하지 않았습니다.
- 캡처 실행 스크립트 [canvas](capture-canvas.mjs)·[CDP 비교](capture-memory.mjs)와 [분석 스크립트](analyze-canvas.py)를 보존합니다. 경로·브라우저 모듈은 해당 제작 환경 기준입니다. 게임 빌드는 이전에 검증한21948a8 전용 production build이며 게임 코드 변경은 없습니다.

[manifest.json](manifest.json)과 `sha256sum -c SHA256SUMS`로 파일을 확인하세요. 기존673233b 영상·21948a8 표시 수정 증거는 변경하지 않습니다. 이 별도 공개 검수 브랜치는 main에 병합·배포하지 않습니다. 검수 후 정리 예정이나 Git 기록·복사본의 완전 삭제는 보장하지 않습니다. 개인 대화·연결 진단·인증정보는 포함하지 않습니다.
